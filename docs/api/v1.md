# Central API v1 Contract

- **Version:** v1
- **Status:** Proposed
- **Date:** 2026-07-14
- **Phase:** Phase 0 Gate 5 — External API and Event serialization
- **Implementation target:** Phase 1 — Local Central MVP
- **Based on:** [Gate 5 API and Event serialization design](../internal/superpowers/specs/2026-07-14-phase-0-api-event-serialization-design.md)
- **Decided by:** [ADR 0006](../adr/0006-adopt-local-v1-api-and-event-serialization.md)

## 1. Transport trust boundary

Phase 1 binds HTTP only to loopback (`127.0.0.1` / `::1`) and serves one trusted local OS account. No LAN, public, remote, or Online Mode API exists.

- CORS is disabled entirely. No `Access-Control-Allow-*` headers are set.
- Every request must originate from the loopback interface and carry the exact configured `Host`; another source or Host returns a safe `403` that discloses no session or Workspace state.
- Unsafe/state-changing methods require exactly one non-null `Origin` equal to the configured loopback application origin. Safe GET/HEAD requests permit an absent Origin for ordinary browser navigation, assets, local clients, health, and metrics; when Origin is present it must be exactly one well-formed non-null matching value. Malformed, multiple, null, or non-matching values always fail closed.
- The server-rendered UI and any local automation share the same bootstrap/session/CSRF flow. There is no bearer-token, API-key, or unauthenticated alternative in Phase 1.
- TLS may be configured; when present, session cookies use `Secure`. The contract requires no TLS in development.

## 2. Bootstrap, session, logout, and CSRF

### 2.1 Bootstrap

`POST /api/v1/session/bootstrap`

Exchanges a high-entropy bootstrap token from protected local configuration for an opaque server-side session.

**Request:**

- `Content-Type: application/json`
- Body: `{"bootstrap_token": "<token>"}`

**Constraints:**

- The bootstrap token is single-use. On successful exchange, the token is rotated in configuration and the old value is invalidated.
- The token never appears in a URL, referrer, Event, error, log, or response body.
- Failed exchanges are throttled. After a configurable threshold, the server returns `429` with `Retry-After`.
- The response contains no token; the session is established via `Set-Cookie`.

**Response (200):**

```json
{
  "schema_version": "v1",
  "request_id": "req_abc123",
  "data": {
    "csrf_token": "csrf_xyz789"
  }
}
```

The Gate 7 server-rendered first-run page reuses this exact endpoint through a same-origin embedded helper; it does not add a second bootstrap mutation or authentication protocol. The helper never places the bootstrap or CSRF token in a URL or persistent browser storage, and navigates to the authenticated application only after the session cookie has been committed successfully.

### 2.2 Session

- Sessions use an opaque server-side identifier.
- The session cookie is set with `HttpOnly; SameSite=Strict; Path=/` (and `Secure` when TLS is configured).
- **Idle expiry:** 30 minutes.
- **Absolute expiry:** 12 hours.
- Sessions are bound to the loopback interface and one trusted local OS account.
- Session expiry, revocation, or absence returns a safe `401` with no enumeration of whether the session ever existed.

### 2.3 Logout

`POST /api/v1/session/logout`

Revokes the current session. Requires a valid session cookie and `X-CSRF-Token` header.

**Response (200):**

```json
{
  "schema_version": "v1",
  "request_id": "req_abc123",
  "data": {}
}
```

The session cookie is cleared via `Set-Cookie` with an expired `Max-Age`.

### 2.4 CSRF

- Every JSON state-changing request (`POST` that submits a domain command) requires a valid `X-CSRF-Token` header.
- The CSRF token is issued with the session on bootstrap and is bound to that session.
- An invalid, missing, or stale CSRF token returns a safe `403` with no session or user disclosure.
- Cross-origin requests are rejected regardless of CSRF token validity (CORS is disabled).
- Requests with an unexpected `Content-Type` (anything other than `application/json` for JSON endpoints) are rejected with a safe `400`.

## 3. Common envelopes

### 3.1 Success envelope

Every successful JSON response uses this structure:

```json
{
  "schema_version": "v1",
  "request_id": "req_abc123",
  "data": {}
}
```

- `schema_version` (string, required): Always `"v1"` for this contract.
- `request_id` (string, required): An opaque correlation identifier for the request. May be client-supplied via `X-Request-Id` or server-generated.
- `data` (object, required): The response payload. Must be present on success; never `null`. Absence of `data` indicates an error response format.

A response must never carry both `data` and `error`.

### 3.2 Error envelope

```json
{
  "schema_version": "v1",
  "request_id": "req_abc123",
  "error": {
    "code": "unauthorized",
    "message": "valid session required",
    "field": null,
    "retryable": false
  }
}
```

- `code` (string, required): A stable machine-readable error code.
- `message` (string, required): A safe human-readable description. Must never include secrets, bootstrap/session/CSRF tokens, raw Artifact bodies, raw filenames, object keys, internal database errors, stack traces, or unbounded untrusted input.
- `field` (string, nullable, optional): The JSON field path related to the error, or `null` if not field-specific. Omitted entirely when not applicable.
- `retryable` (boolean, required): Whether the same request may succeed if retried after the indicated delay.

### 3.3 HTTP status codes

| Status | Meaning |
| --- | --- |
| `200` | Success. |
| `400` | Invalid request (bad JSON, unknown field, bound violation, unexpected Content-Type). |
| `401` | Missing, expired, or revoked session. |
| `403` | Forbidden (invalid CSRF, cross-origin, wrong Host/Origin, cross-Workspace access). |
| `404` | Resource not found or not visible to the session. |
| `409` | Command conflict (idempotency conflict, version conflict). See §8. |
| `413` | Request body exceeds 1 MiB limit. |
| `422` | Valid JSON but invalid command input (missing required field, invalid value). |
| `429` | Rate limited; response includes `Retry-After`. |
| `503` | Transient dependency failure (retryable); response includes `Retry-After`. |

Authorization failures (`401`, `403`) must be non-enumerating: they disclose no information about whether a target resource, Workspace, or session exists beyond what the request itself already carries.

### 3.4 Field conventions

- All identifiers are opaque strings. Clients must not parse, construct, or interpret identifier structure.
- Timestamps are RFC 3339 UTC strings (e.g., `"2026-07-14T12:00:00Z"`).
- Optional fields that are absent are omitted from the response. They are never present with a `null` value.
- Unknown response fields must be ignored by clients.
- Clients must reject an unknown major `schema_version` and fail safely rather than attempting to interpret an unrecognized envelope.

## 4. Content types and bounds

### 4.1 Content types

- All request and response bodies for JSON endpoints use `Content-Type: application/json`.
- Artifact download (`/content`) and preview (`/preview`) endpoints return the Artifact's stored media type with explicit `Content-Type`, not `application/json`.
- Unexpected `Content-Type` values for JSON endpoints are rejected with a safe `400`.

### 4.2 Bounds

| Bound | Value | Enforcement |
| --- | --- | --- |
| JSON command body | 1 MiB (1,048,576 bytes) | Exceeding returns `413`. |
| JSON response body | 2 MiB (2,097,152 bytes) | List endpoints truncate; single-resource responses return `503` with `retryable: false` if the resource exceeds the bound. |
| Single header value | 4 KiB (4,096 bytes) | Exceeding returns `400`. |
| Single path segment / cursor value | 4 KiB (4,096 bytes) | Exceeding returns `400`. |
| JSON nesting depth | 32 levels | Exceeding returns `400`. |

- Artifact byte streams are not JSON and are not subject to the 2 MiB JSON response bound. JSON errors are returned only before bytes start streaming; after bytes begin, the stream is terminated at the TCP level.
- `429` and retryable `503` responses include a `Retry-After` header with a suggested delay in seconds.

## 7. List metadata

Paginated list responses use this structure inside the `data` field:

```json
{
  "schema_version": "v1",
  "request_id": "req_abc123",
  "data": {
    "items": [],
    "next_cursor": "opaque-cursor-value",
    "has_more": true
  }
}
```

- `items` (array): The page of resource summaries. May be empty.
- `next_cursor` (string, nullable): An opaque cursor for the next page, or `null` when there are no more pages.
- `has_more` (boolean): Whether more items exist beyond this page.

Cursor pagination semantics:
- A cursor is opaque, Workspace-bound, and invalid across retention or schema boundaries.
- An invalid or expired cursor returns `400` with a safe message indicating the client must restart from current state.
- Ordering within a list is stable for a given cursor position.
- The full response (including envelope metadata) is bounded by the 2 MiB JSON response limit.

### 7.1 Task list

`GET /api/v1/workspaces/{workspace_id}/tasks`

Query parameters:
- `cursor` (string, optional): Opaque pagination cursor.
- `limit` (integer, optional): Page size, 1–250, default 100.

Response `data`:
```json
{
  "items": [],
  "next_cursor": "opaque-cursor-value",
  "has_more": false
}
```

Each item is a Task summary (§6.1).

### 7.2 Event feed

`GET /api/v1/workspaces/{workspace_id}/events`

Query parameters:
- `after` (string, optional): Opaque cursor from a previous response. Omit for initial page.
- `limit` (integer, optional): Page size, 1–250, default 100.

Response `data`:
```json
{
  "events": [],
  "next_cursor": "opaque-cursor-value",
  "has_more": false
}
```

- `events` (array): Page of Event summaries (§6.10).
- `next_cursor` (string, nullable): Opaque cursor for the next page, or `null`.
- `has_more` (boolean): Whether more Events exist beyond this page.

The feed is a cursor-polling feed, not a live subscription:
- Ordering is stable within one Workspace by immutable Workspace-local `event_sequence`.
- A cursor encodes the last delivered `(workspace_id, event_sequence)` boundary.
- A page is seek-paginated, forward-only, and bounded by the 2 MiB JSON response limit.
- Concurrent later Events appear only after the captured boundary; they cannot cause skips before it.
- The feed may duplicate an Event after a lost response. Clients deduplicate by `event_id` and reconcile from current-state reads.
- Phase 1 retains Events for the supported local MVP lifetime. A future retention watermark must invalidate cursors with `410 cursor_expired`.

## 8. Command headers and replay/version rules

### 8.1 Idempotency-Key

Every state-changing `POST` request must include:

```
Idempotency-Key: <opaque 16–128 byte value>
```

- The value is an opaque string of 16 to 128 bytes chosen by the client.
- The server normalizes the command input and, when the same key, same normalized input, and same scope are seen again, returns the original durable result without appending another Event or transitioning state.
- A changed normalized input or changed expected version (see §8.2) with the same key returns `409 idempotency_conflict`.
- An `Idempotency-Key` with a different scope (e.g., a different Workspace or resource) is an independent operation regardless of key value.
- Missing `Idempotency-Key` on a state-changing request returns `400`.

### 8.2 If-Match

Every state-changing `POST` request that modifies an existing aggregate must include:

```
If-Match: <expected-aggregate-version>
```

- The value is the integer aggregate version the client last read.
- The server rejects the command with `409 version_conflict` if the current aggregate version does not match.
- Clients must re-read current state before retrying with a new version; blind retry is not supported.
- `If-Match` is not required for commands that create new aggregates (e.g., Task creation).

### 8.3 Conflict responses

**Idempotency conflict (`409`):**

```json
{
  "schema_version": "v1",
  "request_id": "req_abc123",
  "error": {
    "code": "idempotency_conflict",
    "message": "command input or version changed under the same idempotency key",
    "field": null,
    "retryable": false
  }
}
```

**Version conflict (`409`):**

```json
{
  "schema_version": "v1",
  "request_id": "req_abc123",
  "error": {
    "code": "version_conflict",
    "message": "aggregate version does not match; re-read current state before retrying",
    "field": null,
    "retryable": false
  }
}
```

Both are non-retryable without corrective client action. The client must re-read the current aggregate state before submitting a new command with a fresh `Idempotency-Key` and matching `If-Match`.

## 9. Artifact download and preview

Artifact delivery is Central-mediated. The server revalidates session authority, Workspace ownership, ready state, sensitivity, disposition, and delete intent immediately before streaming bytes. No presigned or raw object URL is ever exposed.

### 9.1 Download

`GET /api/v1/workspaces/{workspace_id}/artifacts/{artifact_id}/content`

Returns the Artifact body bytes as an attachment.

**Success response headers:**

| Header | Value |
| --- | --- |
| `Content-Type` | The Artifact's stored media type |
| `Content-Disposition` | `attachment; filename="<sanitized-fallback>"` |
| `Cache-Control` | `no-store` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `same-origin` |

**Constraints:**
- Byte ranges (`Range` header) are unsupported in Phase 1.
- Conditional requests (`If-None-Match`, `If-Modified-Since`) are unsupported in Phase 1.
- Errors are returned as JSON before any bytes stream. After bytes begin, errors terminate the stream at the TCP level.
- If the Artifact is not in `ready` status, has pending delete intent, or the session lacks Workspace authority, the server returns a safe `403` or `404` without streaming.

### 9.2 Preview

`GET /api/v1/workspaces/{workspace_id}/artifacts/{artifact_id}/preview`

Returns the Artifact body bytes for inline display, restricted to allowlisted content types only.

**Success response headers:**

| Header | Value |
| --- | --- |
| `Content-Type` | The Artifact's stored media type |
| `Content-Disposition` | `inline` |
| `Cache-Control` | `no-store` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `same-origin` |
| `Content-Security-Policy` | `default-src 'none'; style-src 'unsafe-inline'` |

**Constraints:**
- Preview is restricted to the allowlisted content types defined in the Artifact lifecycle specification ([ADR 0005](../adr/0005-adopt-verified-artifact-lifecycle-and-safe-content-delivery.md)). Types not on the allowlist return `422`.
- The CSP is restrictive: active content never executes in the preview context.
- All delivery revalidation checks from §9.1 apply.
- Preview is bounded; the server may enforce a maximum previewable byte size smaller than the Artifact limit.

### 9.3 Delivery revalidation

Before streaming, the delivery boundary validates:

1. Session authority: the session is valid and not expired.
2. Workspace ownership: the Artifact belongs to the requested Workspace.
3. Ready state: the Artifact status is `ready`.
4. Delete intent: no pending or committed deletion exists.
5. Sensitivity: the Artifact's sensitivity permits the requested delivery mode.
6. Preview eligibility (preview only): the media type is on the allowlist and the size is within preview bounds.

Failure at any check returns a JSON error before bytes stream. The specific check that failed is not enumerated in the error message to avoid information disclosure; the error is safe and non-enumerating.

## 10. Capability discovery

`GET /api/v1/capabilities`

Returns the supported API version and feature set. This endpoint does not require a session.
It remains subject to universal loopback source, exact Host, safe-method optional-Origin validation, header/metadata bounds, method allowlisting, safe observation, and response-security policy; only session and CSRF are exempt.

**Response (200):**

```json
{
  "schema_version": "v1",
  "request_id": "req_abc123",
  "data": {
    "api_version": "v1",
    "feed_contract": "cursor-polling-v1",
    "features": []
  }
}
```

- `api_version` (string): The supported API major version (`"v1"`).
- `feed_contract` (string): The Event feed contract revision (`"cursor-polling-v1"`).
- `features` (array of strings): Optional feature names. Additive fields and types do not invalidate cursors. A major API or feed-order revision does.

## 11. Compatibility and deprecation policy

v1 is additive-only within the major version:

- Adding optional fields to existing resource summaries is compatible.
- Adding new Event types is compatible.
- Adding new endpoints under `/api/v1/` is compatible.
- Adding new features to the capabilities response is compatible.

The following are **not** compatible and require a new major version (v2) or a material ADR to change:

- Changing a field meaning, requiredness, or type.
- Changing an identifier format or ordering contract.
- Changing an authorization rule.
- Changing an Event payload meaning.
- Removing a field from a resource summary.
- Changing the cursor ordering contract.
- Changing the event feed delivery model (e.g., from cursor polling to SSE).

**Deprecation:** A deprecated field remains readable and populated for the current major version. It is removed only when the next major version is introduced. The capabilities response may advertise deprecated features.

**Schema version:** Clients must reject an unknown major `schema_version` and fail safely. The `schema_version` in every response provides a runtime compatibility check independent of the capabilities endpoint.

## 12. API validation scenarios

### Scenario 1: Authorized command flow

A loopback client:
1. Bootstraps a session via `POST /api/v1/session/bootstrap` with a valid bootstrap token.
2. Receives a session cookie and CSRF token.
3. Sends `POST /api/v1/workspaces/{workspace_id}/tasks` with a valid session cookie, `X-CSRF-Token`, `Idempotency-Key`, and a valid Task creation body.
4. Receives `200` with the created Task summary in the `data` envelope.
5. Verifies the Task appears in `GET /api/v1/workspaces/{workspace_id}/tasks`.

Expected: The command succeeds, the durable result is returned, and an Event is appended.

### Scenario 2: Cross-Workspace and unauthorized rejection

A client authenticates for Workspace A and attempts:
- `GET /api/v1/workspaces/{workspace_id_B}/tasks` — returns `403`.
- `POST /api/v1/workspaces/{workspace_id_A}/tasks` without `X-CSRF-Token` — returns `403`.
- A request with `Origin: http://evil.example.com` — returns `403`.
- A safe `GET /api/v1/capabilities` with valid loopback source/Host and no `Origin` — returns `200`; the same GET with null/opaque, malformed, multiple, or non-matching Origin returns `403`.
- An unsafe request with missing, null/opaque, malformed, multiple, or non-matching `Origin` — returns `403`.
- A request after session expiry — returns `401`.
- A bootstrap attempt with an already-used token — returns `429` after throttling threshold.

Expected: All fail without state disclosure or mutation. Error messages are safe and non-enumerating.

### Scenario 3: Lost Event feed response and deduplication

A client:
1. Requests `GET /api/v1/workspaces/{workspace_id}/events` and receives Events with `next_cursor: "c1"`.
2. The TCP response is lost before the client processes it.
3. The client re-requests with the same `after=c0` cursor (or starts fresh).
4. The server returns the same Events (duplicates possible).
5. The client deduplicates by `event_id` and reads current state to reconcile.

Expected: After deduplication and current-state reconciliation, the client converges to the correct state.

### Scenario 4: Invalid cursor and schema version rejection

A client:
- Requests `GET /api/v1/workspaces/{workspace_id}/events?after=expired-or-invalid` — returns `400`.
- Receives a response with `schema_version: "v2"` — the client rejects it and fails safely.

Expected: No blind retry. The client detects the incompatibility before interpreting data.

### Scenario 5: Artifact delivery after state change

Given an Artifact that was `ready` and downloadable:
1. The client begins a `GET /content` request.
2. Before bytes stream, the Artifact is marked for deletion (delete intent recorded).
3. The delivery boundary revalidates and detects the delete intent.
4. The server returns a safe `404` (or `403`) as JSON without streaming any bytes.

Expected: No bytes stream after ready-state or delete-intent change. Same behavior for sensitivity changes and non-ready state.

### Scenario 6: Sentinel absence

Across all endpoints, inspect responses, Events, errors, and cursor values for:
- Bootstrap tokens, session tokens, CSRF tokens.
- Raw Artifact filenames, object storage keys, or presigned URLs.
- Internal database error messages or stack traces.
- Raw secret values or SecretReference bindings.
- Unbounded labels or untrusted input echoed verbatim in `message`.

Expected: None of these appear in any response, Event, error, or cursor.
