# Harness Phase 3g — Resume of an Ambiguous Attempt, Attempt Ceiling and Chain Cost Design

- **Date:** 2026-09-30
- **Status:** Draft. Brainstormed with the recommended option taken for each question, per the maintainer's workflow.
- **Governing decisions:** [ADR 0035](../../../adr/0035-freeze-b09-loop-coordinator-and-adopt-harness-session-boundary.md); [ADR 0036](../../../adr/0036-add-a-separate-harness-launcher-for-operator-harness-sessions.md); the B08 recovery design (leases, fences, prepared successors).
- **Governing spec:** [Harness Adapter Boundary Design](2026-09-27-harness-adapter-boundary-design.md), §7 and §8.
- **Builds on:** phase 3e (`Unclaimed()` follow-up, Mark failed / Mark cancelled), phase 3f (prepared-successor cancel, `evaluateCancel` lease rule) and phase 3d (per-attempt budgets).
- **Investigation:** facts below come from a read-only investigation of the code at `74047ed`.

## 1. Goal

After a serve restart (or a lost lease) an invoked harness attempt is `ambiguous`: nobody knows whether Claude Code finished. Today the operator can only end the Task (`Mark failed`, `Mark cancelled`) and Retry from a fresh clone. 3g adds **Resume**: the operator continues the same Claude Code session in the same clone, as a new StepAttempt of the same Run, under a fixed attempt ceiling and a Task-wide cost budget.

### Non-goals

- **The `rerun` resolution kind.** It stays unproduced. Retry and Rerun keep creating a new Run or Task.
- **An operator-written follow-up prompt.** The prompt is one fixed text (decision 4).
- **Resuming an attempt that is not `ambiguous`,** or one with no recorded session id.
- **Token ceilings.** Tokens stay shown, not capped (3d decision).
- **A cap across Retries.** The ceiling and the cost budget are per Run; a Retry starts a new Run.
- **Changing B08 recovery,** the launcher argv grammar (`--resume <uuid>` is already allowed) or the Claude Code adapter's argv.

## 2. Findings that shape the design

1. **The domain half exists, unused.** `harness.PrepareResume`, `Attempt.Resolve(ResolutionResume)` and `claudecode.Adapter.Resume` (argv `--resume <uuid>`) are built and unit-tested; no production code calls them. `PrepareResume` requires a terminal predecessor with a session id (a `resolved` one must be `resume`), the same Workspace, Run and Kind, the same `Workspace{Path, BaseSHA}`, a non-decreasing fence and a valid budget.
2. **No execution path creates a second StepAttempt for a Step.** A Step in `reconciliation` can reach only succeeded, failed or cancelled; `StartHarnessRun` refuses an existing Step; `ResolveReconciliation` has three dispositions, all of which end the Task and Run. A new command is needed.
3. **The harness/StepAttempt link is by identical UUID** (`AttemptIDForStepAttempt`). A resumed harness attempt therefore needs its own new StepAttempt id. One live harness row per Run is enforced by `harness_attempts_one_live_per_run_idx` (`ambiguous` counts as live), so the ambiguous row must become `resolved` before the resume row is created.
4. **A B08 prepared successor is the right dispatch shape, but not the right identity.** A `running` Task and Run whose current StepAttempt is `prepared` with `predecessor_id` set and no unexpired ownership row is what `queryListDispatchableRuns` lists as `prepared_successor`, and `harnessLifecycle.claimSuccessor` claims it with the ordinary `Claim` command (lease generation = previous + 1; recovery expires ownership rows and never deletes them). B08 **preserves** such an attempt across a restart (`prepared_successor_preserved`, `store.go` ~2238; `CancelPreparedForRecovery` refuses an attempt that already has a predecessor), so it keeps its id and its harness row id. But B08 successors share their predecessor's Step and logical operation id and follow a `cancelled` predecessor; a resume attempt cannot, because every later command on an attempt requires the Step's logical id to equal the attempt's (`lockAndValidateReceiptTarget`), and a Step never goes `reconciliation → running`. The resume attempt therefore lives in a **new Step** (finding 9).
5. **`Provision` cannot be called for a resume.** `gitclone.Provisioner.Provision` deletes and re-creates the Run directory and must run only before `MarkInvoked`. A resumed attempt must reuse the existing clone.
6. **The Run's `OwnershipToken` stays set** after the first claim (`ClaimCurrentRun`, never cleared), so a resumed Run is never `Unclaimed()`: a Cancel on it goes through `RequestCancellation`, and 3f's "Finish cancelling" settles a never-launched resume attempt. This answers the 3e follow-up: **the token is not cleared or rotated**, because the Run is never re-queued, so no path can mistake it for unclaimed.
7. **Cost accounting is per attempt.** `Attempt.Budget` is recorded once at prepare; the native `--max-budget-usd` and Central's `costReached` backstop use it; `RunBudget` (the page) reads only the latest attempt; `Usage.CostMicroUSD` is Claude's `total_cost_usd` (session-cumulative within one process). Whether a *resumed process* restarts that counter at zero is **not yet verified live** (the sanitized `resume.ndjson` fixture suggests it does).
8. **Resume depends on the session file surviving in the harness home** between two launches. The launcher binds a configured harness home directory into each session; that it persists across launches is expected, not yet verified live.
9. **Precedent for a new Step: `create_approval_successor`.** The store already inserts a Step whose id differs from the receipt binding's (`persistSteps`, `insertedStepLogicalOperation`) for that one command scope. 3g adds a second scope of the same kind and leaves every other command's rules as they are.

## 3. Decisions

| # | Question | Decision | Why |
|---|---|---|---|
| 1 | Scope | One operator action, **Resume**, on a Task `waiting(reconciliation)` whose attempt row is `ambiguous` with a session id. Plus the attempt ceiling and the chain cost rule. | The three items are one feature: resume is what creates a chain. |
| 2 | Execution command | A new command `ResumeReconciledAttempt` (`CapabilityWorkspaceOperator`, own command scope, event `attempt_resumed`, own idempotency scope), plus a new `ReconciliationDisposition` `resume` (recorded in the same reconciliation evidence event as the other three; there is no table and no CHECK). **Identity model: a new Step.** In **one commit** it: validates operator attestation evidence (same rules as `ResolveReconciliation`) and the no-active-lease assertion; ends the old StepAttempt and the old Step `failed` (the existing `confirm_failed` state rules; disposition `resume`); inserts a **new Step** (`running`, Sequence = old + 1, new logical id) and a **new StepAttempt** in it (`prepared`, attempt Sequence 1, new StepAttemptId, PhysicalAttemptId and logical id equal to the new Step's, `PredecessorID` = the old attempt); and moves the Task and Run `waiting(reconciliation) → running` through a new task-domain execution transition that **keeps the Run and its OwnershipToken**. No lease is granted; the ownership row stays expired. Narrow, scoped exceptions (spec text, not plan checks): the store persists this scope with update-old plus insert-new rows (rows whose id is the binding's are updated, the others inserted, as the approval-successor scope does for Steps); `validateAttemptInserts` and `validateLogicalOperationReuse` accept a successor whose predecessor is in the same change set moving to `failed` (not `cancelled`) with disposition `resume`, in a **different** Step with a different logical id; `validateChangeSetOwnership` accepts, only in this scope, exactly one inserted Attempts row whose `StepID` is the Step inserted in the same change set (Result, Event and the reconciliation evidence stay bound to the old Step and attempt); nothing else about B08 successors changes. Implementation notes the plan must honour: the exception lives in `validateAttemptIdentities` (the reuse check groups by logical id and cannot see predecessors); `validateAttemptInserts` is called for the inserted row separately; `insertedStepLogicalOperation` gets a resume branch; `reconciliationAttemptState` maps `resume` to `failed`; the old rows are updated before the new ones are inserted (`step_attempts_one_active_run_idx` is not deferrable). | Findings 2, 4, 6, 9. A separate command keeps `ResolveReconciliation`'s three end-the-Task dispositions untouched. A new Step keeps the Step state machine (no `reconciliation → running`) and the Step-to-attempt logical identity that every later command checks. |
| 3 | Who claims and launches | Unchanged dispatch: the resume attempt is listed as `prepared_successor`, `claimSuccessor` claims it (the new Step's logical id matches the attempt's), and the orchestrator launches it. A restart before the claim or before `MarkInvoked` leaves it as it is: B08 **preserves** a prepared attempt that has a predecessor, so the attempt keeps its id and its harness row (decision 5 keys on it). | Finding 4: no new dispatch case. |
| 4 | Prompt | One fixed text owned by the composition: `Continue the task from where the previous run stopped. When finished, give the final report.` The Task instruction is not resent. | No free text from a web form reaches the harness; the session already holds the instruction. |
| 5 | How the orchestrator knows to resume | A new port `ResumeSource(ctx, claimedRun)` is keyed on the **claimed attempt**, never on the Run's latest row: (i) if the claimed StepAttempt's own harness row exists (an earlier claim of the same attempt created it) it is adopted, and it is a resume when its `ResumeOf` is set; (ii) otherwise the harness row of the StepAttempt's `PredecessorID` is the source when it is `resolved(resume)`, or `ambiguous` with the attempt failed and a successor pointing at it, in which case the row's lost `resolved(resume)` write is completed first (decision 6). A source means: `harness.PrepareResume(source, …)`, `adapter.Resume` with `SessionRef{HarnessSessionID: source.HarnessSessionID}` and the fixed prompt. No source means the existing `Prepare`/`Start` path. **The resume path never calls `Provision`, including when it adopts an existing row after a restart.** | Findings 3, 4. A B08 successor of a never-launched first attempt has a `cancelled` predecessor and no source, so it starts normally. |
| 6 | The harness row of the old attempt | After the execution commit, the operator use case calls a new single-attempt method on the harness `Resolver` that records `resolved(resume)` by the operator through `RecoverAttempt`. The recovery authority accepts `resume` as well as `abandon` when the linked StepAttempt is `failed` **and** a StepAttempt in the same Run has it as `predecessor_id` (a new linked state, `LinkedResumed`; B08 predecessors are always `cancelled` and `step_attempts_one_successor_idx` indexes the link), so `confirm_failed` still means abandon and no event JSON is parsed. The startup reconciler heals a lost write the same way (`resolved(resume)`, decided by `recovery:operator_resume`). A compare-and-swap conflict between the route's write and the orchestrator's heal means reload and re-check. | Mirrors 3e's `ResolveAbandon` and the reconciler's lost-write healing. |
| 7 | Workspace | The resumed attempt **does not provision**. A new method on `WorkspaceProvisioner` reopens the Run's existing clone under the rule that everything a harness wrote is untrusted (the `gitclone` package invariant): it runs **no git and reads no clone content**. It verifies `RunDir(run)/repo` through no-follow descriptors and runtime ownership exactly as `seal` does (`openBeneath`, `requireRuntimeDir`), checks that the Run directory carries the provisioned ACLs, and checks free space. The recorded `Workspace{Path, BaseSHA}` must equal the Run's own path. Any mismatch (missing, replaced, sealed by a capture that died half-way) abandons the resume attempt as `workspace_unavailable`, which fails the Task (Retry remains). The launcher's `RESOLVE_NO_SYMLINKS` open stays the backstop at launch. | Finding 5 and the 3a/3b security decision. The recorded `Workspace` is what `PrepareResume` compares. |
| 8 | Attempt ceiling | `CENTRAL_HARNESS_MAX_ATTEMPTS`, default **3**, range 1–10 (1 disables Resume), validated at start like the 3d budget variables (only when harness execution is on). The ceiling counts **Steps of the Run** (Step Sequence), so a B08 successor of a never-launched attempt does not use a slot. The new Step's Sequence must be `<=` the ceiling, checked by the command against a value the trusted composition passes in, and by the page predicate. | Bounds total wall time and spend per Run; per Run because Retry is a separate operator act on a fresh clone. |
| 9 | Chain cost rule | The Task's cost budget is **one budget per Run, pinned to the chain root**: the first harness attempt's recorded `Budget` (with `CostDefaulted` and the wall clock) is the chain's budget, so a restart with a changed `CENTRAL_HARNESS_*` default cannot change it mid-chain. A resumed attempt's recorded `Budget.CostMicroUSD` = the root's cost budget − Σ `Usage.CostMicroUSD` of every earlier harness attempt of the Run (a new read of the Run's harness attempts). Below **US$0.01** remaining (the adapter's native minimum), Resume is refused (`budget_exhausted`). The wall clock stays **per attempt**: each resume gets the root's wall clock; the ceiling bounds the total. The page shows Run cost as the sum of the chain against the root budget. | Money must not multiply with resumes; time is bounded by the ceiling. The rule assumes each process's `total_cost_usd` starts at zero: if it were cumulative, the sum over-counts and Resume stops early — a fail-safe error. The live check (§9) settles which holds. |
| 10 | Known under-count | An ambiguous attempt that never reached a `result` frame has recorded no cost, though it may have spent money. The chain rule counts recorded usage only; the ceiling and wall clock bound the rest. The runbook says so. | Usage reports arrive per turn; nothing more exact exists. |
| 11 | Eligibility (page and command) | Task `waiting(reconciliation)`, the Run's non-terminal Step and StepAttempt in `reconciliation`, harness row `ambiguous` with non-empty `HarnessSessionID` (a variant of `reconciliationTarget`, which also accepts terminal rows), no unexpired lease, Run version unchanged, ceiling not reached, remaining cost ≥ US$0.01, no non-terminal tool-call rows (harness Runs have none). The button `Resume` shows beside `Mark failed`/`Mark cancelled` only when eligible; when the only obstacle is ceiling or budget the panel says `Resume is unavailable: attempt limit reached` / `budget used up`. | Reuses `resolveTarget` of 3e. |
| 12 | Route | `POST /app/tasks/harness/resume`, the same prelude as the resolve action (Origin, session CSRF, active session, claimability gate). Principal `operator-session:<p>`. Refusals map as for resolve; a live lease gives the retryable 409. | Reuse. |
| 13 | Failure after resume | A resumed attempt is an ordinary attempt: it can succeed (report, patch and commits captured as in 3b), fail, hit its budget, be cancelled (3e), or go `ambiguous` again (then Resume again, up to the ceiling). A `claude --resume` that cannot find its session exits non-zero and the attempt fails normally. | No special cases. |

## 4. Data flow

1. Serve restarts mid-Run. The reconciler makes the attempt `ambiguous`; B08 moves the Step and StepAttempt to `reconciliation`; the Task is `waiting(reconciliation)`.
2. The operator opens the Task and presses **Resume**. The route builds `ResumeReconciledAttempt` from the current aggregate (expected versions, ceiling, remaining budget) and commits it: old Step and StepAttempt `failed`, a new Step `running` with a new StepAttempt `prepared` (predecessor = the old one), Task and Run `running`.
3. The route asks the `Resolver` to record the old harness row `resolved(resume)`. If that write fails, serve logs it; the commit is authoritative, the Task is already `running` and the page redirects normally, reporting nothing. The claim in step 5, or else the next start's reconciler, completes the write. This is safe because a resume attempt is never started as an ordinary one: a Step of Sequence > 1 with no source is `ErrResumeUnavailable`, not a fresh provision.
4. The dispatcher lists the Run as `prepared_successor` and `claimSuccessor` claims it (lease generation + 1).
5. The orchestrator calls `ResumeSource` (keyed on the claimed attempt), reopens the clone without git, `PrepareResume`s the new harness row (budget = remaining), marks the StepAttempt invoked and launches `claude --resume <session>` with the fixed prompt. The session reveals the same session id.
6. Usage folds per attempt as today; the page adds the chain.

## 5. Errors

| Situation | Behaviour |
|---|---|
| Double click / two operators | Expected versions or `harness_attempts` one-live index refuses the second: 409 or replay. |
| Lease unexpired | Retryable 409, nothing written. |
| Ceiling reached or budget below US$0.01 | Button hidden with the one-line reason; the command refuses the same. |
| Harness write after the commit fails | Task is `running`, StepAttempt `prepared`. Serve logs the failure and the page reports nothing (it redirects normally). The claim heals the row before launching (decision 5), else the next start's reconciler does. |
| Serve stops between the commit and the claim, or after the resume row was created and before `MarkInvoked` | B08 **preserves** the prepared resume attempt (same id, same harness row). On re-claim `ResumeSource` adopts the attempt's own row (`ResumeOf` set) and the resume path runs; `Provision` is never called, so the clone survives. |
| Cancel before the claim | The Task is claimed, so the cancel goes through `RequestCancellation`; 3f's "Finish cancelling" settles the never-launched attempt. |
| Clone missing or replaced | Attempt abandoned `workspace_unavailable`; Task fails; Retry available. |
| Session not found by claude | Attempt fails; Task fails; Retry available. |
| Harness disabled or no operator composed | No button, no route. |

## 6. Security

- The action needs the same session, CSRF, Origin and `CapabilityWorkspaceOperator` as `Mark failed`; the command carries attestation evidence and asserts no active lease. No permission check is weakened.
- The prompt is a constant; nothing from the request reaches the harness. The session id comes from the harness row, never from the request.
- `--resume` opens a session file the harness itself wrote under the harness home; the launcher's closed argv grammar is unchanged.
- The resumed attempt runs under the Task's recorded permission policy and the same launcher scope as any attempt. The clone was written by an untrusted process before the ambiguity; capture at the end seals and reads it exactly as for a first attempt (3b), so no capture rule changes.
- The chain budget and ceiling bound what a repeated Resume can spend.

## 7. Testing

- **Execution domain:** table test for `ResumeReconciledAttempt` (allowed from `reconciliation` with an expired or absent lease; refused with an unexpired lease, a stale version, a ceiling hit, a `succeeded`/`failed` attempt, non-terminal tool calls); the change set has exactly the old Step and attempt `failed`, a new Step (Sequence + 1, new logical id) `running`, a new attempt `prepared` in it with the old attempt as predecessor, one `resume` reconciliation evidence, Task and Run `running` with the same OwnershipToken; the two scoped exceptions accept only this shape (a same-Step or `cancelled`-predecessor variant of it is still refused where it was before).
- **Task domain:** the new transition keeps the Run id and token; refuses non-reconciliation waits.
- **Postgres (live, isolated DB):** the command commits atomically and is idempotent; the partial indexes (`step_attempts_one_active_run_idx`, `..._one_successor_idx`) hold; the dispatch query lists the result as `prepared_successor`; `Claim`, `MarkInvoked` and a settle succeed on the resume attempt; B08 recovery over it reports `prepared_successor_preserved`; `RecoverAttempt` accepts `resume` only for a `failed` StepAttempt that has a successor (`LinkedResumed`); a `confirm_failed` attempt still resolves as abandon; the summed cost read.
- **Harness app:** orchestrator resume path with fakes (`PrepareResume`, `adapter.Resume` with the session ref and the fixed prompt, no `Provision`, the recorded remaining budget, the healing of a lost `resolved(resume)` write, a missing clone); reconciler lost-write healing; the ordinary start path unchanged.
- **Config:** `CENTRAL_HARNESS_MAX_ATTEMPTS` table test (default, 1, 10, 0, 11, non-numeric).
- **Web:** button only when eligible; reasons for ceiling and budget; CSRF/Origin/session/claimability as the resolve route; 409 on a live lease; the page's chain cost.
- **e2e (`cmd/central`, fake claude):** stop serve mid-attempt, restart, Resume, launch resumes the session and succeeds with artifacts; two resumes reach the ceiling and the third is refused; Resume then Cancel before claim settles; budget shrinking across a chain; **stop serve after the resume harness row is created and before `MarkInvoked`, restart: the clone is kept and the session is resumed** (no `Provision`).
- **Live/reference host (maintainer):** see §9.
- **Docs:** runbook (§8 Resume, the under-count, `CENTRAL_HARNESS_MAX_ATTEMPTS`), `docs/implementation/current-phase.md`.

## 8. Plan-stage checks

1. Whether `commandScope`/`commandEventKind`/lease-policy tables in `postgres/execution/store.go` need entries for `resume_reconciled_attempt`/`attempt_resumed`, and whether any DB constraint ties `step_attempts.predecessor_id` to the same Step (the reconciliation disposition is only a JSON field in an evidence event: no migration for it).
2. The new task-domain transition: which Task/Run fields `ExecutionResumeSameRunRequest` sets that this one must not (`RetryEligibleAt`, waiting reason), and the event kind.
3. That `Claim` and every later fenced command accept the resume attempt (new Step logical id equal to the attempt's), and that the two scoped exceptions of decision 2 do not loosen any other command's checks (test that a normal `Claim`, a B08 successor and an approval successor are refused or accepted exactly as before).
4. `harness.PrepareResume` requires a non-decreasing fence: confirm the new fence (lease generation + 1) is accepted after the ambiguous row's fence.
5. The B08 recovery scan over a `running` Run whose current attempt is a lease-less `prepared` resume attempt: it must **preserve** it (`prepared_successor_preserved`), not create a successor. Pin with the live recovery tests (Architecture mode), and check every reader that assumes one Step per Run (`reconciliationTarget`, page projections, recovery scans, `LatestAttemptForRun`).
6. `WorkspaceProvisioner`'s new reopen method (decision 7): which of `seal`'s helpers (`openBeneath`, `requireRuntimeDir`, `provisionedRunACLs`) it can share without exporting harness-controlled reads, and the ACL state of a Run directory whose capture never started versus one whose capture died half-way.

## 9. Acceptance

1. An operator can Resume an ambiguous attempt from the Task page; the Task returns to `running`, the same Run continues the same Claude session in the same clone, and on success ends `succeeded` with report, patch and commits.
2. The old Step and StepAttempt are `failed` (disposition `resume` in the reconciliation evidence) and the old harness row is `resolved(resume)`; a **new Step** (Sequence + 1, new logical id) holds a new StepAttempt (`prepared`, predecessor = the old attempt); the Run id and OwnershipToken are unchanged.
3. With ceiling N, a Step of Sequence > N is never created: at N Steps the Resume is refused and hidden with the reason. A B08 successor of a never-launched attempt does not use a slot.
4. A resumed attempt's recorded budget is the chain root's cost budget minus earlier recorded cost, and its wall clock is the root's; below US$0.01 Resume is refused.
5. A restart between the commit and the launch, including one after the resume row was created and before `MarkInvoked`, loses nothing (the clone is kept and the session is resumed); a Cancel before the claim settles through "Finish cancelling".
6. No path other than `resume` changes: Mark failed, Mark cancelled, Retry, Rerun and the first-attempt start behave as before.
7. **Maintainer gate (not run by agents):** on the reference host with real claude, (a) `--resume` finds the session in the launcher's harness home after a restart; (b) the resumed process's `total_cost_usd` is per-process (or cumulative — the runbook records which and the rule stays fail-safe either way); (c) the resumed run captures its artifacts.
8. The full portable suite passes apart from the known `internal/recovery` `TestNoC06SuiteSourceOutsideTheRunnerCallsTestingSkipDirectly` failure, and touched packages pass against live PostgreSQL, including the B08 recovery tests.
