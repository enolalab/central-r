# ADR 0035 harness phase 3l: a token ceiling for harness attempts

Date: 2026-09-30. Follows phase 3k (PR #20, `24343ff`). No migration.

## 1. Problem

Cost (phase 3d, 3g, 3j) and wall clock are bounded; tokens are only shown ("Tokens are shown, not capped", runbook §4b). Claude Code has no native token limit flag, and the adapter reports usage only from the final `result` frame, so a token ceiling cannot stop a Run mid-way today. The real stream does carry per-message usage on `assistant` frames (`message.id`, `message.usage`), with each message repeated once per content block.

Goal: an optional serve-wide ceiling on the tokens one harness attempt may use, enforced by Central during the Run from the per-message usage, with the same stop path and outcome rules as the cost backstop.

## 2. Decisions

| # | Topic | Decision | Why |
|---|---|---|---|
| 1 | What counts | The ceiling counts "billed tokens" = `TokensIn + TokensOut + CacheWrite` of the attempt's recorded usage. Cache reads are excluded: every API call re-reads the whole context, so summing them inflates without meaning (real fixtures: input_tokens 10, cache_creation 34951, cache_read 13689 to 48640 per request). | Cache creation, input and output are new work; cache read is not. |
| 2 | Config | `CENTRAL_HARNESS_MAX_TOKENS`: a plain positive integer, range 100,000 to 1,000,000,000, no separators (a real first response alone writes 30,000 to 35,000 cache tokens, so a lower ceiling would stop every Run at its first response). Unset: no ceiling, behaviour unchanged. Validated only while harness execution is enabled, with the existing config error shape. One serve-wide value, applied to each attempt separately; a resumed attempt gets the full value again (a new process restarts its counters), so a Run's total is bounded by `CENTRAL_HARNESS_MAX_ATTEMPTS` times this value and by the cost chain rule. It is not recorded on the attempt row and there is no per-Task token budget: both need a migration and are out of scope. | Env-only, like the phase 3j cap, keeps the phase migration-free. |
| 3 | Live signal | The Claude Code adapter parses `message.id` and `message.usage` (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`) of `assistant` frames whose `parent_tool_use_id` is null (the main thread), de-duplicates by `message.id` (a message repeated per content block counts once; per counter the largest value seen for that id wins), keeps a running sum over distinct messages, and emits a `UsageReport` (scope `session_cumulative`, Estimated true) whenever a new message raises the sum. Subagent frames (`parent_tool_use_id` set) are not counted live: it is not established that the `result` includes them, so the live figure is a lower bound. Output tokens of an `assistant` frame are a partial stream snapshot (6 versus 31 in the fixture), also a lower bound. | Mid-run stop needs a mid-run number; the lower bounds only make the ceiling fire late, never falsely. |
| 4 | Monotonic reports | `ApplyUsage` refuses any decrease, so the adapter never sends one: each counter of a live report is the maximum of what it already emitted and the new live figure, its cost field carries the cost already emitted (0 before the first result), and the `result` report takes, per token counter, the maximum of what was emitted and its own turn-summed total. The adapter keeps its existing `addTurn` result sum (the value that becomes the result report) separate from the emitted maximum, so a later turn's result is never added on top of a live-inflated base. The recorded final usage is therefore the larger of the live sum and the result's figure; live output tokens stop rising in later turns until the live sum catches up with the emitted maximum. | Keeps the domain rule intact; the recorded figure stays Estimated. |
| 5 | Enforcement | The orchestrator gets `tokensReached`, the twin of `costReached`: after an applied `UsageReport`, when a ceiling is configured, the attempt's billed tokens are at or above it, no budget cause has fired, no cancel is in progress and the attempt is not terminal, it stops through the existing budget path (stop answering permissions, `Interrupt`, grace timer, kill) with a new budget cause `budget_tokens`. Outcome rules as for cost: an adapter-reported budget terminal keeps its reason; a succeeded terminal stays succeeded; an interrupted, killed or failed terminal caused by Central's stop becomes `TerminalBudget` with reason `budget_tokens`; the first budget cause wins; a cancel wins over both. | One stop path, one set of outcome rules. |
| 6 | Bound | The stop fires between API responses and then follows interrupt and grace kill, so an attempt can overshoot the ceiling by one response plus the grace period, and the final `result` can show more than the ceiling. Subagent tokens are not counted live. Both are documented, not fixed. | The honest limit of a Central-side ceiling with no native flag. |
| 7 | Vocabulary and page | `budget_tokens` is added wherever `budget_cost` and `budget_wall_clock` are known, in BOTH vocabularies: the orchestrator's reason codes (`internal/harness/ports.go`, the `budgetCause` code) and the execution domain's closed `FailureReason` set (`internal/execution/harness_run.go`), because serve maps any code outside that set to `execution_failed` (`cmd/central/harness_lifecycle.go`) and the Task page reads the Task's reason, not the attempt's; then the operator-facing failure text on the Task page, the runbook §6 reasons table and the runbook reasons list. No database vocabulary is involved (the reason columns are free text with only a length check). The page adds no new line for the ceiling itself. | Consistency with the cost reasons. |
| 8 | Docs | Runbook §4b replaces "Tokens are shown, not capped" with the ceiling, its definition, the lower-bound and overshoot limits, the resume behaviour (full value per attempt) and the env var; `docs/implementation/current-phase.md` one line; §10 (maintainer gate) gets one added check: with a real host, a Run started under `CENTRAL_HARNESS_MAX_TOKENS=100000` on a task that needs more ends `budget_tokens`, with recorded billed tokens (tokens in + out + cache write) at or above 100,000 (it proves the live parsing against a real stream; the agents cannot). | Operator-facing behaviour; the live frame shape is only proven by fixtures here. |

## 3. Data flow

`harnessConfig` parses the env var into `MaxTokens` and passes it to the orchestrator config. Adapter: `onAssistant` (main thread, new message id) emits a `UsageReport`; `onResult` emits its report with the maxima of decision 4. Orchestrator: `apply` folds each report, `drive` checks `costReached` then `tokensReached` after each applied report and runs the existing stop path with the matching cause; `budgeted` maps the terminal by the cause. Nothing else reads the ceiling.

## 4. Errors

- Invalid env value: serve refuses to start (existing config error shape).
- A frame without `message.id`, without `usage`, with a negative counter or with `parent_tool_use_id` set: ignored for the live sum (never an error).
- A usage report that would decrease a counter cannot be produced by the adapter (decision 4); the domain still refuses one from any other adapter, as today.

## 5. Acceptance

1. Config: unset (no ceiling), valid, below the range, above the range, malformed and separators refused; harness off ignores the variable.
2. Adapter (fixtures, no live claude): the real `bridge-allow.ndjson` (the two-message fixture: live 35,555 billed tokens versus 35,755 in its result) and `success.ndjson` / `resume.ndjson` (one distinct message id each, repeated per content block, so they prove de-duplication within a message only) produce live reports with one report per distinct message id and a sum equal to the sum over distinct ids of in + out + cache_write; a hand-made multi-message stream with a subagent frame (`parent_tool_use_id` set; it is null in every real fixture) counts only the main thread; every emitted report is monotonic per counter including the final result report (a result figure below the live sum keeps the live sum, and a later turn is not added on a live-inflated base). The adapter tests that pin exact event sequences and "exactly one usage report" (`session_test.go`) are updated to the new sequences, each change explained in the plan; no other adapter behaviour changes.
3. Orchestrator (fake adapter emitting token reports mid-script): at or above the ceiling the attempt is interrupted and, when the process ignores the interrupt, killed after the grace, ending `budget_exhausted` with reason `budget_tokens` and the Task/Run failing with reason `budget_tokens` (not `execution_failed`); below the ceiling nothing happens; no ceiling configured behaves as today; a succeeded terminal stays succeeded; an adapter `TerminalBudget` keeps its own reason; the first cause wins over a later cost or wall clock cause and a cancel wins over tokens.
4. Live e2e (`CENTRAL_TEST_PG_URL` and runtime URL, `-p=1`): a Task dispatched with a ceiling under a scripted adapter that reports tokens past it ends `failed` with the attempt `budget_exhausted` / `budget_tokens`, the Task/Run reason `budget_tokens` and the recorded usage tokens; without the ceiling the same script succeeds. The script follows the 3d pattern (a token usage report followed by a permission request that waits for an answer), or the script could finish succeeded before the stop lands.
5. `gofmt`, `go vet ./...` (also `-tags referencehost`), `go build ./...` clean; runbook (§4b, reasons, §10) and `current-phase.md` updated.

## 6. Out of scope

A per-Task requested token budget and a recorded per-attempt token budget (both need a migration), a token sum across a resume chain or across Retries, subagent tokens, a native flag (none exists), a cap on cache reads, thinking-token estimates (`system/thinking_tokens`), and the 3d to 3f Minors.
