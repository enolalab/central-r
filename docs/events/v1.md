# Event v1 Contract

- **Version:** v1
- **Status:** Proposed
- **Created:** 2026-07-14
- **Related:** [ADR 0006](../adr/0006-adopt-local-v1-api-and-event-serialization.md), [Gate 5 design](../internal/superpowers/specs/2026-07-14-phase-0-api-event-serialization-design.md), [Durable execution](../architecture/durable-execution.md)

## 1. Event authority

An Event is immutable audit-and-recovery evidence, not a second current-state model. PostgreSQL normalized rows are authoritative for scheduling, lifecycle, and UI state. Events record durable transition proof: who, what, when, from-state, to-state, and reason.

Every accepted domain transition appends its Event in the same PostgreSQL transaction as current-state updates. Phase 1 does not reconstruct current state by replaying Events.

No actor, adapter, or observer may mutate a committed Event. A delivered Event is never altered by delivery state, outbox processing, or downstream consumption.

Events are Workspace-scoped. Every Event carries a durable `workspace_id` and is only observable within that Workspace.

## 2. Envelope format

Every v1 Event serializes as a JSON object with these required fields:

| Field | Type | Description |
| --- | --- | --- |
| `event_id` | opaque string | Unique immutable Event identity. |
| `event_sequence` | positive integer | Durable Workspace-local sequence number. Assigned server-side; see section 7. |
| `schema_version` | string `"v1"` | This contract version. |
| `type` | string | Discriminated Event type, e.g. `task.created`, `run.started`. |
| `occurred_at` | RFC 3339 UTC string | When the transition was accepted. |
| `workspace_id` | opaque string | Owning Workspace. |
| `aggregate_type` | string | Domain aggregate kind, e.g. `task`, `run`, `step`. |
| `aggregate_id` | opaque string | Aggregate identity within the Workspace. |
| `aggregate_version` | positive integer | Aggregate version after this transition. |
| `correlation_id` | opaque string | Scope-wide correlation identifier. |
| `causation_id` | opaque string | Immediate cause Event or command identity. |
| `actor` | object | See section 3. |
| `payload` | object | Type-discriminated allowlisted payload. See section 4. |

Applicable contextual fields appear alongside the required fields when the aggregate context defines them:

| Field | Type | Description |
| --- | --- | --- |
| `task_id` | opaque string | Parent Task identity. |
| `run_id` | opaque string | Parent Run identity. |
| `step_id` | opaque string | Parent Step identity. |
| `attempt_id` | opaque string | Parent StepAttempt or ToolCallAttempt identity. |
| `prior_state` | string or null | Aggregate state before the transition. Omitted when there is no prior state (e.g. creation). |
| `next_state` | string | Aggregate state after the transition. |
| `reason` | string or null | Safe reason code for the transition, e.g. `approval`, `retry_delay`, `reconciliation`. May be null when inapplicable. |

Fields omitted when not applicable; they are never set to `null` unless the field allows it explicitly (see above). Unknown envelope fields must be ignored by consumers.

### Example: task.created

```json
{
  "event_id": "evt_abc123",
  "event_sequence": 42,
  "schema_version": "v1",
  "type": "task.created",
  "occurred_at": "2026-07-14T12:00:00Z",
  "workspace_id": "ws_789",
  "aggregate_type": "task",
  "aggregate_id": "task_456",
  "aggregate_version": 1,
  "correlation_id": "corr_xyz",
  "causation_id": "cmd_create_001",
  "actor": {
    "actor_id": "session_001",
    "actor_kind": "session"
  },
  "task_id": "task_456",
  "next_state": "created",
  "payload": {
    "type": "task.created.v1",
    "task_kind": "agent.run",
    "task_count": 1
  }
}
```

## 3. Actor allowlisting

The `actor` object is allowlisted to:

| Field | Type | Description |
| --- | --- | --- |
| `actor_id` | opaque string | Actor identity, e.g. session ID or system identity. |
| `actor_kind` | string | Actor kind: `session`, `system`, `executor`. |

No other actor fields are permitted. Specifically excluded: display names, email addresses, IP addresses, real user identities, tokens, or credentials.

## 4. Type-discriminated, versioned payload allowlist

Every `payload` object contains a required `type` discriminator naming the Event-type-specific schema, e.g. `task.created.v1`.

Payload values are restricted to:

- opaque related IDs (`task_id`, `run_id`, `step_id`, `attempt_id`, `approval_id`, `artifact_id`, `checkpoint_id`, `tool_call_id`)
- safe state strings (`prior_state`, `next_state`, `reason` codes)
- bounded non-negative counters (e.g. `attempt_count`, `run_count`)
- safe UTC timestamps in RFC 3339
- safe policy and version fingerprints (opaque fingerprint strings, no raw policy content)

Explicitly excluded from every Event payload:

| Exclusion | Reason |
| --- | --- |
| Task input or tool input | May contain PII, secrets, or unbounded content. |
| Backend locator (provider endpoint, model URL) | Infrastructure detail; leaks topology. |
| Destination or path detail | May expose filesystem layout or object-store structure. |
| Raw operation input | Unbounded and untrusted. |
| Body content (Artifact, response, or any raw bytes) | Never carried in Event payloads. |

Payload implementation guidance: payloads must be shallow structures with no nested objects deeper than level 3 within the payload itself (the overall envelope depth limit of 8 applies to the full serialized document).

## 5. Redaction, size, and depth limits

Before serialization, every Event payload is source-redacted: the producer removes excluded fields, strips unsafe metadata, and ensures the payload conforms to the allowlist in section 4.

Serialization limits:

| Limit | Value | Enforcement |
| --- | --- | --- |
| Total serialized Event size | ≤ 32 KiB | Producer must reject before commit; exceeding Events must not be appended. |
| JSON nesting depth | ≤ 8 | Measured from the root object. |
| Payload depth within the payload object | ≤ 3 | See section 4. |

A producer that cannot redact an Event to 32 KiB or below must fail the transition safely — it must not truncate, silently drop fields, or append a degraded Event.

## 6. Secret material exclusion

Event payloads must never contain:

- bootstrap, session, or CSRF tokens
- SecretReference plaintext or raw secret values
- raw Artifact bodies or preview content
- raw filenames (sanitized names are excluded too; only opaque `artifact_id` references are permitted)
- object-store keys, bucket names, or presigned URLs
- unbounded labels or untrusted user-provided text
- internal database connection strings or error details
- raw provider or model credentials

Sanitized display labels (e.g. a task display name under a bounded length) are not unbounded labels and are permitted when explicitly approved in a future enrichment Event type. Phase 1 v1 payloads carry no display labels.

## 7. Workspace-local event sequence

Every Event carries a durable, immutable `event_sequence` integer assigned within a single Workspace.

Properties:

- `event_sequence` is unique and strictly increasing within one Workspace.
- Normal transactional allocation is gap-free: rejected commands and rolled-back transactions consume no sequence. Restore, import, or a governed forward corrective migration may introduce a missing number, so consumers must not treat numerical continuity as proof of completeness.
- `event_sequence` is assigned atomically with the Event append in the same domain transaction.
- No ordering guarantee is made across Workspaces.
- Concurrent appends across independent aggregates within a Workspace are ordered by commit time; the sequence reflects this durable commit order.

The logical Event order is `(workspace_id, event_sequence)`. This is the seek key for cursor polling.

## 8. Cursor poll semantics

`GET /api/v1/workspaces/{workspace_id}/events` is a polling-only feed, not a live subscription. No SSE, WebSocket, webhook, or push delivery exists in Phase 1.

A cursor is an opaque string encoding the last delivered `(workspace_id, event_sequence)` boundary. The cursor is Workspace-bound and meaningless outside its Workspace.

### Request

```
GET /api/v1/workspaces/{workspace_id}/events?after=<opaque-cursor>&limit=<n>
```

- `after` — optional opaque cursor. When absent, the feed starts from the earliest available Event.
- `limit` — optional integer, defaults to 100, maximum 250 (see section 9).

### Response

```json
{
  "schema_version": "v1",
  "request_id": "opaque",
  "data": {
    "events": [ /* Event envelopes */ ],
    "next_cursor": "<opaque-cursor>",
    "has_more": true
  }
}
```

- `events` is ordered by Workspace-local `event_sequence` ascending.
- `next_cursor` encodes the boundary of the last Event in this response. Pass it as `after` to get the next page.
- `has_more` is `true` when Events exist beyond this page; `false` when the feed is exhausted.

### Forward-only seek pagination

The feed is forward-only. A cursor represents a strict seek boundary: the next page returns only Events whose `event_sequence` is strictly greater than the cursor boundary. There is no backward pagination and no random-access offset.

## 9. Limit defaults and bounds

| Parameter | Default | Minimum | Maximum |
| --- | --- | --- | --- |
| `limit` | 100 | 1 | 250 |

Values outside 1–250 return a safe `400` response. The response is bounded by the common 2 MiB response limit; if a single Event exceeds the JSON response bound, the producer must have rejected it at append time per section 5.

## 10. No-skip guarantee

A cursor boundary captures the highest `event_sequence` delivered.

- The next page returns Events strictly after that boundary.
- Concurrent Events appended after the cursor was issued appear only on the next page after the boundary — they cannot cause the current page to skip Events before the boundary.
- A page is an ordered slice of the committed Workspace Events visible when the page is assembled; consumers do not require the returned sequence numbers to be numerically contiguous.

There is no "skip" mechanism. If a consumer misses Events (e.g. due to cursor expiry), the only recovery is a full current-state reload followed by a new feed from the latest available cursor (see section 12).

## 11. Duplicate and recovery behavior

A lost HTTP response after a successful Event append can cause the next poll to return Events that were already delivered.

- The feed does not guarantee exactly-once delivery.
- Clients must deduplicate by `event_id`.
- After a gap or duplicate, clients reconcile by reading current-state representations from the resource endpoints (`GET /api/v1/workspaces/{workspace_id}/tasks/{task_id}`, etc.) and resuming the feed with the latest cursor.

Exactly-once delivery is not promised. Cross-Workspace ordering is not promised.

## 12. Cursor expiry

A cursor is invalid after:

- crossing a retention boundary (see section 13),
- a major schema version change,
- a Workspace-scoped feed-order revision.

An invalid or expired cursor returns:

- HTTP `410 Gone`
- `code: "cursor_expired"`
- safe `message` instructing the client to reload current state and start a new feed from the earliest available cursor.

Clients must not attempt to repair or reinterpret an expired cursor. The only valid recovery is: reload current state from resource endpoints, then start a fresh Event feed.

## 13. Event retention boundary

Phase 1 retains Events for the supported local MVP lifetime. Events are not pruned, archived, or aged out during Phase 1.

Pruning, retention watermarks, and cursor-invalidation-at-boundary behavior are deferred to Gate 6. The Gate 6 specification must:

- define the retention policy (time-based, count-based, or both),
- ensure that expired cursors return `410 cursor_expired`,
- provide a `(workspace_id, event_sequence)` seek index for cursor resolution.

Phase 1 storage is unbounded; Gate 6 must constrain it before any production deployment.

## 14. Outbox non-mutation

The domain transaction that appends an Event may also create an outbox delivery record referencing that immutable Event.

- An outbox delivery record stores the Event identity and delivery state.
- Delivery state (e.g. `pending`, `delivered`, `failed`) never alters the Event envelope or payload.
- Delivery retries, dead-lettering, or expiry are outbox concerns and do not modify Event content.

Outbox persistence, delivery queries, and publication mechanisms are Gate 6 implementation work. Phase 1 exposes Events only through the polling feed described in section 8.

## 15. Compatibility

`v1` is additive-only:

| Change | Compatibility |
| --- | --- |
| Add an optional envelope or payload field | Compatible. |
| Add a new Event `type` | Compatible. |
| Add a new `actor_kind` value | Compatible. |
| Change a field meaning or requiredness | Breaking; requires new major version or material ADR. |
| Change an identifier format | Breaking. |
| Change feed ordering | Breaking; invalidates cursors. |
| Remove a field | Breaking. |
| Change an authorization or security rule | Breaking. |

Deprecated fields remain readable for the supported major version. A future major version may remove them after a transition period announced in a capabilities endpoint.

Additive optional fields and new Event types do not invalidate cursors. A major API version or feed-order revision does invalidate cursors (see section 12).

`GET /api/v1/capabilities` returns the supported API major, feed contract revision, and optional feature names. Clients use this to negotiate format expectations before interpreting payloads.

## 16. Observability

Event production and consumption must be observable:

- The producer must expose a count metric of appended Events by `type`, including rejected oversized or unredactable Events.
- The feed endpoint must expose metrics for pages served, cursor misses (`410 cursor_expired`), and duplicate deliveries (client-reported or server-inferred).
- Every Event must carry consistent `correlation_id` and `causation_id` to enable tracing of causal chains.
- Durable execution recovery (startup scan, stale-ownership resolution) must log when reconciliation or replay decisions are made, referencing Event identity without exposing payload details.
- Event rejection at append time (size, depth, redaction failure, secret material detection) must be logged as a durable error with safe metadata (Event type, aggregate identity, rejection reason) and no raw payload content.

Exact metric and log schemas are deferred to Gate 6 (persistence) and Gate 7 (Go handler implementation).

## 17. Validation scenarios

### Scenario 1: Append and poll one Event

A domain transition creates a `task.created` Event within Workspace A. The Event is appended atomically with the current-state write. A client polls `GET /api/v1/workspaces/ws_a/events` without a cursor and receives the Event in `events`, a `next_cursor` encoding `(ws_a, 1)`, and `has_more: false`.

Pass condition: exactly one Event returned, `next_cursor` present, `has_more: false`.

### Scenario 2: Forward-only cursor progression

Workspace A has Events at sequences 1, 2, and 3. Client polls with `after=<cursor-for-seq-1>&limit=1` and receives only Event 2. Next poll with `after=<cursor-from-prior-response>` receives Event 3.

Pass condition: each page contains only the expected Event; no Event is skipped; cursor boundaries are respected.

### Scenario 3: Concurrent append does not cause skip

Client polls Workspace A with cursor encoding sequence 1. While the page is assembled, a concurrent domain transaction appends Event at sequence 2. The response includes Event 2 only if the page assembly captured it; if it did not, the next cursor still encodes sequence 1 and the next poll returns Event 2. In neither case is Event 2 skipped.

Pass condition: no gap in delivered sequences across sequential polls.

### Scenario 4: Duplicate delivery after lost response

Client polls and receives Event at sequence 1 with `next_cursor` for sequence 1. The HTTP response is lost. Client polls again with the same `after` cursor and receives the same Event again.

Pass condition: client deduplicates by `event_id`; duplicate does not cause incorrect state interpretation.

### Scenario 5: Expired cursor returns 410

An Event at sequence 1 falls outside the retention boundary (simulated or future Gate 6 retention policy). Client polls with a cursor encoding sequence 0.

Pass condition: response is HTTP `410 Gone` with `code: "cursor_expired"` and a safe message. Client reloads current state and starts a new feed.

### Scenario 6: Oversized payload rejected

A producer attempts to append an Event whose serialized size exceeds 32 KiB after best-effort redaction.

Pass condition: Event is not appended; transition fails; producer logs rejection reason without the raw payload.

### Scenario 7: Secret material absent from feed

A domain transition involves a SecretReference resolution. The Event payload contains only opaque SecretReference ID and safe fingerprint, never plaintext. A Task creation Event payload contains no bootstrap token, session token, or CSRF token.

Pass condition: polling the feed after each transition returns Events with no tokens, secrets, raw filenames, object keys, or unbounded labels.

### Scenario 8: Outbox delivery does not mutate Event

An Event is appended with a corresponding outbox delivery record. The outbox delivery state transitions from `pending` to `delivered`.

Pass condition: polling the feed returns the Event unchanged; `event_id`, payload, and all envelope fields are identical regardless of outbox delivery state.

### Scenario 9: New Event type is compatible

A future Gate adds a `step.heartbeat` Event type with an optional `heartbeat_count` field. A v1 client that ignores unknown `type` values continues to poll and deduplicate by `event_id`.

Pass condition: existing v1 client receives the new Event type without error; cursor continues to function; `schema_version` remains `"v1"`.
